# Offline conversion benchmark

This developer-only harness compares htomd with five converters. It uses only
standard-library measurement/reporting code. Competitors and their transitive
requirements live in separate, hash-pinned `locks/*.txt` files; they are never
installed in the project's development environment or added to package dependencies.
Nothing under `tools` or `.benchmark` ships in either distribution.

## Reproduce

Initial measurements target macOS ARM64 with the repository's Python 3.14.7 and
uv 0.12.11. Install these with mise, then run from the repository root:

```sh
mise install
mise run setup
mise run benchmark:smoke
mise run benchmark
```

Each invocation builds a fresh htomd wheel and recreates six isolated environments
under ignored `.benchmark/`. Installation and wheel retrieval need network access;
conversion uses only local HTML, with no fetching or external cleanup. Binary wheels
are required so compilation toolchains cannot silently affect the installation
comparison. Setup errors stop the command with their underlying error.

`benchmark:smoke` checks every adapter against the same short article and requires
a string containing `Steep the tea`; this is an API check, not quality scoring.
`benchmark` writes `.benchmark/results.json`, checkpointing after each speed worker.
The initial reference results are retained as `results/macos-arm64.json` and the
human-readable [report](results/macos-arm64.md). To deliberately replace them:

```sh
cp .benchmark/results.json tools/benchmark/results/macos-arm64.json
mise run benchmark:report
mise exec -- python -m tools.benchmark.report tools/benchmark/results/macos-arm64.json --readme --check
```

The [optimization comparison](results/optimization.md) records the subsequent
before/after measurements and code-size changes. The initial unoptimized run is
preserved in `results/macos-arm64-baseline.json`; the main report and README use
the latest full run.

The optimized runtime measured under the development version `0.1.0` is released
as `0.1.1`. Saved version labels and wheel hashes identify the measured artifacts;
they are not rewritten when preparing a release.

The reporting command reads saved JSON; it does not run a benchmark. For a separate
experiment or seed, use `mise exec -- python -m tools.benchmark.run --seed 42
--output .benchmark/experiment.json`, then `mise exec -- python -m
tools.benchmark.report .benchmark/experiment.json` to create an adjacent report.
Avoid other CPU-intensive work while measuring. No commits or package publication
are performed by these commands.

## Measurement contract

- All **115 existing sanitised snapshots** are read in sorted ID order and decoded
  using the corpus manifest's encoding, before any timed conversion. Every input's
  SHA-256 must match the manifest. Snapshots are not changed. Their separate
  [provenance and licensing](../../tests/fixtures/real/README.md) still apply.
- Six libraries run sequentially, in five fresh interpreter rounds. A recorded
  pseudorandom seed (default `20260909`) determines library order in each round.
  Document order stays fixed. A worker warms up on one complete corpus pass, then
  performs at least five measured passes and at least two seconds of timed work.
- `perf_counter_ns` measures each public adapter call. Corpus time is the sum of
  the 115 per-document times, excluding output validation, lengths, bookkeeping,
  loading, imports and warm-up. Garbage collection stays enabled; no explicit
  collection or tuning is applied. One caller converts one document at a time.
- The reported corpus time is the median of five round medians, giving each fresh
  worker equal weight. The range is the minimum–maximum of those round medians,
  not a confidence interval. Throughput uses input bytes and that median.
  Relative speed is **competitor corpus time / htomd corpus time**: above 1 means
  htomd is faster. Raw JSON preserves every pass and every document timing.
- Each library has three additional fresh RSS workers, each converting one full
  loaded corpus. Reported RSS is the median process high-water mark, including
  interpreter, standard-library harness overhead, imports, loaded decoded inputs,
  conversion temporaries and native allocations. Output strings are released
  between documents. Timing history is not retained. `ru_maxrss` is bytes on
  macOS and KiB on Linux; the accounting helper tests both conventions. This
  initial runner requires macOS ARM64; other platforms remain future work.
- Import duration is the median of 20 fresh interpreters. Only `time` is explicitly
  imported before timing `__import__(module)` in a minimal script. Interpreter
  startup and result serialization are excluded. Workers run with `-I -B`
  (isolated imports, no generated bytecode); filesystem caches may be warm.
- Wheel size is the compressed wheel for the **root package only**. For competitors,
  the published wheel matching the installed distribution's WHEEL tags is downloaded
  and checked against PyPI's SHA-256. Its filename, hash and URL are saved. htomd
  uses the freshly built local wheel. Installed footprint sums logical file bytes
  owned by all installed distributions, including transitive dependencies, metadata
  and console scripts. It excludes interpreter, installer tooling (`pip`,
  `setuptools`, `wheel`), harness, symlinks and generated bytecode. It is not physical
  filesystem allocation. A generated README changes wheel metadata size on later
  builds; the recorded wheel hash identifies the artifact actually measured.
- Every worker has a five-minute timeout. Exceptions, unexpected output types,
  crashes and timeouts remain visible; other libraries continue. Empty strings
  and Trafilatura's `None` are recorded as empty outputs, not exceptions. All
  warm-up/measured pass output lengths and diagnostics are saved outside timing.
  Incomplete timing runs have no complete-corpus throughput or speed ratios.
  RSS/import tables use successful samples, with sample counts in the detailed
  report. Worker stderr is retained verbatim in JSON.
- JSON records UTC start/end, CPU, RAM, OS, Python/uv/package versions, source
  revision and dirty state, source/harness/lock hashes, wheel hashes, corpus hashes,
  adapters, measurement settings and randomized orders. Dirty state is expected
  for the initial uncommitted implementation; source hashes identify its code.

## Implementation and dependency context

The generated reports identify the conversion implementation and count extra Python
packages from the saved isolated installations. These are the dependencies of the
pinned versions on Python 3.14.7/macOS ARM64 with no optional extras selected:

| Library | Implementation | Direct Python dependencies | Total including transitive |
| --- | --- | ---: | ---: |
| htomd 0.1.0 | Pure Python, stdlib HTMLParser | 0 | 0 |
| markdownify 1.2.3 | Python, BeautifulSoup using stdlib HTMLParser | 2 | 4 |
| html2text 2025.4.15 | Pure Python, stdlib HTMLParser | 0 | 0 |
| Trafilatura 2.2.0 | Python with native C via lxml | 7 | 16 |
| html-to-markdown 3.12.2 | Rust core with Python bindings | 0 | 0 |
| htmd-py 0.1.2 | Rust core with Python bindings | 0 | 0 |

Direct requirements were checked against the installed distributions' `Requires-Dist`
metadata, excluding optional extras. markdownify directly requires BeautifulSoup and
six. Trafilatura directly requires certifi, charset-normalizer, courlan, htmldate,
justext, lxml and urllib3. Total counts exclude the root library, interpreter and
installer tools and include distinct direct/transitive Python distributions. The
full versioned dependency lists are in the saved JSON and detailed report.

Zero Python package dependencies does not mean pure Python or no native dependencies:
the Rust converters bundle compiled code in their wheels, and lxml wraps the C
libraries libxml2/libxslt. Rust crates and bundled C libraries are not counted as
separately installed Python packages. Installed size captures their bundled bytes.
Standard-library implementations also use native interpreter/stdlib code; “pure
Python” describes the converter package and its selected parsing path here.

Implementation sources: markdownify's installed default `bs4_options='html.parser'`;
[Trafilatura's LXML usage](https://github.com/adbar/trafilatura/blob/master/docs/usage-python.md),
[lxml's native libraries](https://lxml.de/),
[html-to-markdown's Rust core](https://github.com/xberg-io/html-to-markdown/tree/main/packages/python),
and [htmd-py's Python bindings](https://github.com/lmmx/htmd).
Context7 ID `/adbar/trafilatura`, requested version `2.2.0`, was checked for the LXML
path; `/xberg-io/html-to-markdown`, requested version `3.12.2`, for the native core.
The exact installed APIs and metadata supplement those branch-tracking documents.

See the [quality evaluation proposal](QUALITY.md) for separate extraction and
conversion-fidelity scorecards. Quality evaluation is proposed, not yet implemented;
the current unreviewed annotations cannot support a quality ranking.

## Adapters and documentation

Versions were resolved from PyPI's current stable releases on **2026-09-09**.
Context7 was consulted first with the exact IDs and requested versions below;
its returned documents track repository branches, not guaranteed version snapshots.
The installed locked versions were then verified by the shared smoke test.

| Package/version | Public adapter (all other settings default) | Context7 library ID | Official source |
| --- | --- | --- | --- |
| htomd 0.1.0 | `htomd.convert(html)` | Local repository, not queried | [Implementation](../../python/src/htomd/__init__.py) |
| markdownify 1.2.3 | `markdownify.markdownify(html)` | `/matthewwithanm/python-markdownify` | [README](https://github.com/matthewwithanm/python-markdownify) |
| html2text 2025.4.15 | `html2text.html2text(html)` | `/alir3z4/html2text` | [README](https://github.com/Alir3z4/html2text) |
| Trafilatura 2.2.0 | `trafilatura.extract(html, output_format="markdown")` | `/adbar/trafilatura` | [API](https://trafilatura.readthedocs.io/en/latest/corefunctions.html) |
| html-to-markdown 3.12.2 | `html_to_markdown.convert(html).content` | `/xberg-io/html-to-markdown` | [Python API](https://github.com/xberg-io/html-to-markdown/blob/main/docs/reference/api-python.md) |
| htmd-py 0.1.2 | `htmd.convert_html(html)` | No matching library found; official fallback | [PyPI documentation](https://pypi.org/project/htmd-py/0.1.2/) |

htomd's `convert()` includes content selection and metadata extraction. Trafilatura
selects main content; only its output format is overridden. markdownify, html2text
and htmd-py convert markup. html-to-markdown uses its default conversion result,
including metadata, and the adapter returns its `.content` string. No URL is
supplied to any converter, and no default is changed to make outputs more similar.
The workloads therefore differ in output length, extraction behavior and formatting.
This is a performance comparison on these snapshots, not a quality ranking.

To refresh one lock deliberately, resolve a stable version from PyPI, verify its
API, then compile its entire dependency closure, for example:

```sh
mise exec -- uv pip compile - --python 3.14.7 --generate-hashes \
  --output-file tools/benchmark/locks/markdownify.txt <<'REQ'
markdownify==1.2.3
REQ
```

Repeat for each competitor and rerun smoke/full measurements. Locks are independent
so each package resolves and installs its own dependencies without contamination
from another converter. `mise run check` covers the harness with Ruff, strict mypy
and deterministic offline tests. After `mise run package:sources` and
`mise run package:native`, `mise run test:packages` checks both Python archives and verifies
that htomd installs and runs without benchmark packages. The harness does not tune
converter settings. Concurrency, scheduled CI and regression thresholds remain deferred.
